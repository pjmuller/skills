# Learn in the owning reference

An explicit user correction or verified routing failure can refine durable policy.
Record the smallest generalizable pattern, with bounded scope, date and evidence
reference (thread/artifact ID); do not retain sensitive ticket/mail bodies as rules.
One ticket's wording does not establish a company-wide policy. State uncertainty
when evidence supports only a provisional rule.

Edit the existing owner: project boundaries in the project catalog, ticket/workflow
precedents in its triage reference, account rules in the account wrapper. Trigger
gaps or wrong intent matches belong in the wrapper's private lookup
([pattern](onboarding.md#trigger-lookup)); update its row without duplicating owning policy.
Cross-cutting lessons may use a small private reference if none fits; keep it bounded (roughly
40 lines), replacing superseded rules rather than accumulating contradictions.
Read the existing rule first, preserve unrelated policy, and allow later correction
or removal. Do not save these lessons in harness-native memory.

Split before writing: would another operator's router need the mechanic? Yes → the
canonical public core (`t3-route` or `t3-manage-thread`) with a neutral reproduction
and relevant review/tests; the wrapper keeps only its private value (model, account,
path, person, workspace) and a link. Neutral wording alone does not prove a rule is
universal; a user's standing preference stays private. Do not mutate installed copies, create public
issues containing private evidence, or automatically publish a private example.

Verify the owning edit by reading it back and replaying the corrected case without
external writes. Commit/push accepted corrections under the owning repository's
policy; distinguish a proposal or local edit from persisted shared policy. Report
the changed decision and scope, not a new policy essay.
