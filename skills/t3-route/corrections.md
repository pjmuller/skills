# Learn in the owning reference

An explicit user correction or verified routing failure can refine durable policy. Record the
smallest generalizable pattern with bounded scope, date and evidence reference (thread/artifact
ID); never keep sensitive ticket/mail bodies as rules. One ticket's wording is no company-wide
policy; mark provisional rules as such.

Edit the existing owner: project boundaries → project catalog; ticket/workflow precedents → its
triage reference; account rules → account wrapper; trigger gaps or wrong intent matches → the
private lookup ([pattern](onboarding.md#trigger-lookup)), without duplicating owning policy.
Cross-cutting lessons with no owner → one small private reference (~40 lines), replacing
superseded rules rather than accumulating contradictions. Read the existing rule first, keep
unrelated policy. Never save these lessons in harness-native memory.

Split before writing: would another operator's router need the mechanic? Yes → the public core
(`t3-route` or `t3-manage-thread`) with a neutral reproduction and relevant tests; the wrapper
keeps only its private value (model, account, path, person, workspace) and a link. Neutral
wording does not make a standing preference universal. Never mutate installed copies, file
public issues with private evidence, or auto-publish a private example.

Verify by reading the edit back and replaying the corrected case without launching or external
writes.
Commit/push under the owning repo's policy; distinguish a proposal or local edit from persisted
shared policy. Report the changed decision and scope, not a policy essay.
